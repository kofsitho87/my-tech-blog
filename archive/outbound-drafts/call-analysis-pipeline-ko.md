## 1. 들어가며

### 1.1 이전 글과의 연결

[이전 글](./livekit-hospital-voice-agent-en.md)에서 LiveKit Agents를 활용한 병원 Voice AI 시스템 구축 경험을 공유했습니다. Multi-Agent 아키텍처, 예약 처리, 정보 검색까지 다뤘는데요.

이번 글에서는 **통화가 종료된 후** 일어나는 일에 대해 이야기합니다. 통화가 끝나면 "이 통화에서 무슨 일이 있었지?"라는 질문에 답해야 합니다. 예약이 완료되었는지, 환자가 긍정적으로 반응했는지, 상담원 연결이 필요했는지, 통화 내용을 어떻게 요약할지 등을 파악해야 합니다.

### 1.2 통화 분석이 필요한 이유

Voice AI 통화가 끝나면 여러 가지 후처리가 필요합니다.

**문제 1: 실시간 STT 오류**

실시간으로 처리하다 보니 음성 인식 품질이 완벽하지 않습니다. 예를 들어 환자가 "내일 오전 10시에 예약할게요"라고 말했는데, STT가 "내일 오전 ten시에 예약할 게요"처럼 혼합 언어 오류를 발생시키는 경우가 있습니다.

**문제 2: 통화 결과 파악**

수백 건의 통화가 발생하면, 각 통화에서 무슨 일이 있었는지 일일이 확인하기 어렵습니다.

| 통화 | 결과 | 후속 조치 |
| ---- | ---- | ---- |
| A | 예약 완료 | 없음 |
| B | 상담원 요청 (연결 실패) | 콜백 필요 |
| C | 인사 중 끊김 | 재시도 검토 |
| D | 긍정 응답 | 리마인드 완료 |

**문제 3: 요약 필요**

상담원이 후속 조치를 하려면 통화 내용을 빠르게 파악해야 합니다.

### 1.3 이 글에서 다루는 내용

이 글에서는 다음을 다룹니다:

- **음성 전사 교정**: Gemini로 STT 오류 교정
- **대화 분석**: LLM으로 메타데이터 추출
- **대화 요약**: 환자 관점 자동 요약
- **파이프라인 구현**: RabbitMQ 기반 비동기 처리

다루지 않는 내용:

- RabbitMQ 설치 및 설정 (공식 문서 참조)
- LLM API 기본 사용법

참고: 이 글에서는 내부 리소스 식별자(큐 이름, 서비스 이름, 로그 이벤트 키)를 비식별화하여 표기합니다.

## 2. 시스템 아키텍처

### 2.1 전체 파이프라인 구조

전체 시스템은 Voice Agent System과 Conversation Analysis Pipeline 두 부분으로 나뉩니다.

**Voice Agent System**에서는 LiveKit Agent Session이 통화를 진행하며 대화를 기록합니다. 세션이 종료되면 RabbitMQ를 통해 통화 분석 시작 큐(예: `call-analysis-start`)로 메시지를 발행합니다.

**Conversation Analysis Pipeline**에서는 메시지를 수신하여 3단계 처리를 수행합니다:

1. **Step 0 - Transcriber**: Gemini 2.5 Pro를 사용하여 음성 전사 교정
2. **Step 1 - Analyzer**: Claude Sonnet 4.5 또는 GPT-4.1을 사용하여 대화 메타데이터 추출
3. **Step 2 - Summarizer**: GPT-4.1을 사용하여 대화 요약 생성

처리가 완료되면 결과를 백엔드 API(DB 저장)와 이벤트 버스(실시간 이벤트 전파)로 발행합니다.

### 2.2 비동기 처리 방식

통화 분석은 **비동기로** 처리합니다.

동기 처리 방식에서는 통화 종료 후 분석이 끝날 때까지 30초 정도 대기해야 다음 통화를 처리할 수 있어 비효율적입니다. 반면 비동기 처리 방식에서는 통화 종료 즉시 MQ에 메시지를 발행하고 바로 다음 통화를 처리할 수 있습니다. 분석은 별도의 서비스에서 처리됩니다.

**비동기 처리의 장점:**

- Voice Agent는 통화 처리에만 집중
- 분석 서비스 독립적 스케일링 가능
- 분석 실패해도 통화 서비스에 영향 없음

### 2.3 핵심 컴포넌트

| 컴포넌트 | 역할 | 사용 모델 |
| ---- | ---- | ---- |
| **Transcriber** | STT 오류 교정, 타임스탬프 측정 | Gemini 2.5 Pro |
| **Analyzer** | 대화 메타데이터 추출 | Claude Sonnet 4.5 / GPT-4.1 |
| **Summarizer** | 대화 요약 생성 | GPT-4.1 |
| **MQ Consumer** | 메시지 수신 및 처리 흐름 관리 | - |
| **MQ Producer** | 분석 결과 발행 | - |

## 3. 음성 전사 교정 (Step 0)

### 3.1 실시간 STT의 한계

OpenAI Realtime API를 사용한 실시간 음성 처리는 빠르지만, 완벽하지 않습니다.

**발생하는 문제들:**

| 문제 유형 | 예시 | 빈도 |
| ---- | ---- | ---- |
| **Ghost Message** | 침묵이 "네네네"로 인식 | 높음 |
| **혼합 언어 오류** | "10시" → "ten시" | 중간 |
| **순서 뒤바뀜** | 사용자 응답 순서 오류 | 낮음 |
| **누락** | 짧은 응답 미인식 | 중간 |

**Ghost Message란?**

실제로 환자가 말하지 않았는데 STT가 인식한 가짜 메시지입니다. 예를 들어 실제 오디오에서는 환자가 침묵하거나 주변 소음만 있는데, STT 인식 결과에는 "네 알겠습니다"라는 존재하지 않는 발화가 기록되는 경우입니다.

### 3.2 Gemini 기반 교정 시스템

해결책은 **원본 오디오를 다시 듣는 것**입니다.

입력으로 Original STT Conversation(텍스트)과 Audio File(실제 녹음 파일)을 받아서, Gemini 2.5 Pro(멀티모달 LLM)가 처리한 후, 출력으로 Corrected Conversation(교정된 텍스트)과 start_time(각 발화 시작 시간)을 생성합니다.

**왜 Gemini인가?**

Gemini 2.5 Pro는 오디오 파일을 직접 이해할 수 있는 멀티모달 모델입니다. 오디오와 텍스트를 함께 보고 교정할 수 있습니다.

**처리 과정:**

1. 오디오 파일 다운로드 (CDN에서 가용할 때까지 대기)
2. 오디오를 Base64로 인코딩
3. 프롬프트 로드 (모델별로 다른 프롬프트)
4. Gemini에 오디오와 함께 전송
5. 구조화된 출력으로 결과 받기

### 3.3 Ghost Message 처리

Ghost Message를 판별하는 기준:

**Ghost Message 삭제 조건:**

- 오디오에서 해당 발화가 들리지 않음
- 침묵 또는 노이즈만 존재
- 맥락상 불필요한 발화

**Ghost Message 유지 조건 (예외):**

- DTMF 메시지 (키패드 입력, 오디오 없음이 정상)
- 불확실한 경우 (잘 안 들리지만 있을 수도)
- Assistant/Developer 메시지 (Ground Truth)

**DTMF 처리가 중요한 이유:**

DTMF(Dual-Tone Multi-Frequency)는 전화 키패드 입력 신호입니다. 예를 들어 환자가 주민번호 뒷자리를 입력하면 "DTMF: 000102"와 같이 기록됩니다.

DTMF는 음성이 아니므로 오디오 파일에 없는 게 정상입니다. Ghost Message로 오인해서 삭제하면 안 됩니다.

### 3.4 프롬프트 설계

전사 교정 프롬프트의 핵심 지침들:

**1. Message Filtering & Reordering**

- Remove Ghost Messages: 오디오에 없으면 삭제
- Keep ALL DTMF Messages: DTMF는 절대 삭제 금지
- Reorder Sequences: 실제 오디오 순서대로 재정렬

**2. Editing Scope**

- Modifiable: user 메시지의 content만 수정 가능
- Immutable: assistant, developer 메시지는 절대 수정 금지

**3. Metadata Handling**

- role: 원본 유지
- interrupted: 원본 유지
- start_time: user만 측정, 나머지는 null

**start_time 측정 가이드:**

- **정의**: 사용자 발화의 첫 음절이 시작되는 정확한 시점 (초 단위)
- **제외 대상**: 침묵, 숨소리, 배경 소음
- **측정 절차**: 이전 assistant 발화 종료 시점 확인 → assistant 종료 ~ user 시작 간격 측정 → 이전 타임스탬프와 비교하여 순서 확인
- **형식**: Float (예: 21.5, 37.8)
- **제약**: 나중 메시지는 반드시 더 큰 start_time

## 4. 대화 분석 (Step 1)

### 4.1 메타데이터 추출 목표

대화에서 다음 정보들을 자동으로 추출합니다:

**상담원 연결 관련:**

| 필드 | 설명 | True 조건 |
| ---- | ---- | ---- |
| `transfer_call_request` | 상담원 연결 성공 | 상담원 연결 작업 성공 로그 존재 (예: `[TRANSFER_OPERATION: RESULT=SUCCESS]`) |
| `agent_consultation_request` | 상담원 연결 필요 (미완료) | 연결 시도했으나 실패/미완료 |

**통화 종료 관련:**

| 필드 | 설명 | True 조건 |
| ---- | ---- | ---- |
| `end_call_due_to_delay` | 응답 지연으로 종료 | 시스템이 자동 종료 |
| `end_call_by_user_after_greeting` | 인사 후 종료 | 인사 완료 후 바로 끊김 |
| `end_call_by_user_during_greeting` | 인사 중 종료 | 인사 도중 끊김 |
| `end_call_by_user_rejection` | 거절 후 종료 | 환자가 거절 의사 표시 후 종료 |

**예약 관련:**

| 필드 | 설명 | True 조건 |
| ---- | ---- | ---- |
| `reservation_creation_complete` | 예약 생성 완료 | 예약 생성 성공 로그 존재 (예: `[RESERVATION_CREATE: RESULT=SUCCESS]`) |
| `reservation_creation_incomplete` | 예약 생성 미완료 | 예약 시작했으나 완료 안 됨 |
| `reservation_inquiry_complete` | 예약 조회 완료 | 예약 조회 성공 로그 존재 (예: `[RESERVATION_LOOKUP: RESULT=SUCCESS]`) |
| `reservation_cancellation_request` | 예약 취소 요청 | 환자가 취소 의사 표시 |
| `reservation_change_request` | 예약 변경 요청 | 환자가 변경 의사 표시 |

**응답 관련:**

| 필드 | 설명 | True 조건 |
| ---- | ---- | ---- |
| `positive_response` | 긍정 응답 | 예약 확인에 "네, 갈게요" 등 |
| `unclear_response` | 불분명한 응답 | 맥락에 맞지 않는 응답 |
| `information_inquiry` | 정보 조회 완료 | 정보 조회 성공 로그 존재 (예: `[INFO_LOOKUP: RESULT=SUCCESS]`) |

### 4.2 trustcall을 이용한 구조화 출력

#### trustcall이란?

[trustcall](https://github.com/hinthornw/trustcall)은 LangChain 팀의 William Hinthorn이 개발한 라이브러리로, LLM에서 **신뢰할 수 있는 구조화된 출력**을 추출하기 위해 만들어졌습니다.

LLM에게 복잡한 JSON 스키마를 생성하거나 수정하도록 요청하면 종종 실패하거나 예상치 못한 결과가 나옵니다. trustcall은 이 문제를 **JSON Patch 연산** 방식으로 해결합니다. 전체 JSON을 다시 생성하는 대신, LLM에게 수정이 필요한 부분만 패치하도록 요청하여 더 안정적이고 비용 효율적인 결과를 얻습니다.

#### trustcall의 핵심 장점

| 장점 | 설명 |
| ---- | ---- |
| **빠르고 저렴한 생성** | 전체 스키마 재생성 대신 패치 연산으로 비용 절감 |
| **복잡한 스키마 지원** | 중첩된 Pydantic 모델도 안정적으로 처리 |
| **검증 오류 자동 재시도** | 유효성 검사 실패 시 자동으로 패치하여 수정 |
| **정보 손실 방지** | 기존 데이터 업데이트 시 원치 않는 삭제 방지 |

#### 기본 사용법

trustcall을 사용하려면 먼저 pip로 설치합니다: `pip install trustcall`

사용 과정은 크게 세 단계로 나뉩니다:

**1단계: 스키마 정의**

Pydantic의 BaseModel을 상속받아 추출하고자 하는 데이터 구조를 정의합니다. 각 필드에는 타입과 함께 Field의 description 파라미터로 상세한 설명을 작성합니다. 이 설명이 LLM이 어떤 정보를 추출해야 하는지 이해하는 데 핵심적인 역할을 합니다.

예를 들어 사용자 프로필을 추출하려면 `user_name` 필드에 "사용자의 이름"이라는 설명을, `interests` 필드에 "사용자의 관심사 목록"이라는 설명을 추가합니다.

**2단계: Extractor 생성**

`create_extractor` 함수를 사용하여 LLM과 스키마를 연결합니다. 주요 파라미터는 다음과 같습니다:

- `llm`: 사용할 LLM 인스턴스 (예: ChatOpenAI, ChatAnthropic)
- `tools`: 추출에 사용할 Pydantic 모델 리스트
- `tool_choice`: 사용할 도구 이름 (모델 클래스 이름과 동일)
- `enable_inserts`: True로 설정하면 새 레코드 생성과 기존 레코드 업데이트를 동시에 지원

**3단계: 추출 실행**

생성된 extractor의 `invoke` 메서드에 메시지를 전달하면 구조화된 결과가 반환됩니다. 입력은 `messages` 키에 대화 내용을 담은 딕셔너리 형태입니다. 결과는 `responses` 키에 Pydantic 모델 인스턴스 리스트로 반환됩니다.

#### 우리 프로젝트에서의 활용

대화 분석에서는 `ConversationMetadataForLLM`이라는 Pydantic 모델을 정의하여 통화에서 추출할 메타데이터 스키마를 정의했습니다. 각 필드(예: `positive_response`, `reservation_creation_complete`)에는 상세한 description을 작성하여 LLM이 정확하게 판단할 수 있도록 가이드합니다.

예를 들어 `agent_consultation_request` 필드는 "AI가 해결하지 못해 상담원 상담이 여전히 필요한 상태"를 나타내며, True 조건으로는 developer 로그에서 상담원 연결 시도가 실패/미완료된 경우(예: `[TRANSFER_OPERATION: RESULT=REQUESTED/FAILED/ERROR]`)나 assistant가 "상담원에게 전달해 두겠습니다" 등으로 후속 조치를 약속한 경우가 있습니다.

#### trustcall vs with_structured_output

LangChain의 기본 `with_structured_output` 메서드와 비교했을 때 trustcall의 차별점:

| 항목 | with_structured_output | trustcall |
| ---- | ---- | ---- |
| 복잡한 스키마 | 실패 가능성 높음 | 안정적으로 처리 |
| 검증 오류 시 | 단순 재시도 | 패치로 부분 수정 |
| 기존 데이터 업데이트 | 전체 재생성 | 변경 부분만 패치 |
| 비용 | 전체 토큰 재생성 | 패치만 생성하여 절감 |

특히 우리 프로젝트처럼 15개 이상의 boolean 필드와 복잡한 조건을 가진 스키마에서는 trustcall이 훨씬 안정적인 결과를 제공합니다.

### 4.3 Hard Rules 적용

LLM 판단만으로는 부족한 경우, **규칙 기반 보정**을 적용합니다.

**Hard Rule 1: information_inquiry**

정보 조회 성공 로그가 있을 때만 True로 설정합니다. LLM이 대화 내용만 보고 True로 판단해도, 실제 로그에 대응되는 성공 로그(예: `[INFO_LOOKUP: RESULT=SUCCESS]`)가 없으면 False로 보정합니다.

**Hard Rule 2: transfer_call_request**

상담원 연결 성공 로그가 있을 때만 True로 설정합니다. 대화에서 "상담원 연결해주세요"라고 했더라도, 실제 연결 성공 여부는 로그로 판단해야 합니다.

**Hard Rule 3: 상호 배타적 관계 강제**

`transfer_call_request=True`이면 `agent_consultation_request=False`로 설정합니다. 상담원에게 성공적으로 연결되었다면, "상담원 연결 필요" 상태는 아니기 때문입니다.

**왜 Hard Rules가 필요한가?**

LLM만 사용할 때 문제가 발생합니다. 예를 들어 대화 내용이 "상담원 연결해주세요" → AI: "연결해드리겠습니다"인 경우, LLM은 `transfer_call_request = True`로 판단할 수 있습니다. 하지만 실제로는 연결 시도만 했고, 성공 여부는 로그를 봐야 합니다.

로그에 연결 요청 기록(예: `[TRANSFER_OPERATION: RESULT=REQUESTED]`)만 있고 성공 기록이 없다면, Hard Rule로 `transfer_call_request = False`, `agent_consultation_request = True`로 보정합니다.

### 4.4 프롬프트 설계의 어려움

분석 프롬프트에서 가장 어려운 부분은 **STT 오류를 감안한 해석**입니다.

**기본 원칙:**

오디오 품질 및 STT 한계로 인해 사용자 메시지는 대화 맥락에 맞지 않거나 불분명한 내용이 포함될 수 있습니다. user 메시지가 맥락에 부합하지 않으면, assistant 메시지의 반응 패턴을 우선적으로 분석합니다.

**AI 응답 패턴 분석 기준:**

- AI가 "확인해주셔서 감사합니다"로 긍정 해석한 경우
- AI가 예약 확정, 변경 완료 등 다음 단계로 진행한 경우
- 통화 종료 사유가 정상 완료인 경우

**예외 상황 (AI 응답 패턴 분석 적용 안 함):**

- AI가 "다시 말씀해주시겠어요?"로 재확인 요청한 경우
- AI가 오류 처리 프로토콜을 실행한 경우

**적용 예시:**

user가 "뭐야?"라고 맥락상 불분명하게 응답했지만, assistant가 "확인해주셔서 감사합니다. 12월 17일 10시 예약 안내드립니다."라고 긍정으로 해석하고 진행했다면, `positive_response = True`로 판단합니다 (AI 반응 패턴 기반 판단).

## 5. 대화 요약 (Step 2)

### 5.1 요약 형식 설계

요약은 두 가지 필드로 구성됩니다:

- **title**: 한 줄 요약 제목
- **content**: 간결한 요약 본문

출력 예시로는 title이 "예약 확인 - 환자 참석 의사 확인"이고, content가 "- 12월 17일 오전 10시 정형외과 예약 안내 / - 환자 참석 의사 확인 완료 / - 주차 안내 제공"과 같은 형태입니다.

### 5.2 환자 관점 요약

요약의 핵심은 **환자의 액션/반응** 기준입니다.

**요구사항:**

- title: 아웃바운드 목적 + 환자의 최종 상태/요청사항을 한 줄로 요약
- content: 핵심 내용만 간결하게 서술. 불필요한 사담 제외하고, 후속 액션(재예약, 상담 필요 등)에 필요한 내용만 포함

**좋은 요약 vs 나쁜 요약:**

나쁜 요약은 과정을 나열합니다: "AI가 인사를 하고 예약을 안내했습니다. 환자가 응답했습니다. AI가 다시 확인했습니다. 환자가 확인했습니다. 통화가 종료되었습니다."

좋은 요약은 결과 중심입니다: title은 "예약 리마인드 - 참석 확인 완료"이고, content는 "12월 17일 10시 정형외과 예약 확인 / 환자 참석 의사 명확히 확인 / 추가 문의 없이 정상 종료"입니다.

## 6. 실전에서 마주친 문제들

### 6.1 Audio 파일 가용성

통화가 끝나자마자 분석을 시작하면, 녹음 파일이 아직 CDN에 업로드되지 않은 경우가 있습니다.

통화 종료 후 녹음 파일이 S3에 업로드되고(1-2초), CloudFront 캐시가 전파되어(2-5초) 파일에 접근 가능해지기까지 시간이 걸립니다. 하지만 MQ 메시지는 즉시 발행되므로, 분석 서비스가 메시지를 수신했을 때 파일이 아직 없어서 404 Error가 발생할 수 있습니다.

**해결: Polling with Retry**

오디오 파일이 CDN에 가용할 때까지 대기하는 로직을 구현했습니다. HEAD 요청으로 파일 존재 여부를 확인하고, 없으면 일정 시간 후 재시도합니다.

| 파라미터 | 값 | 이유 |
| ---- | ---- | ---- |
| `max_retries` | 15 | 최대 45초 대기 (충분한 여유) |
| `retry_interval` | 3초 | CDN 전파 시간 고려 |
| `timeout` | 5초 | HEAD 요청은 빨라야 함 |

### 6.2 STT Hallucination

STT가 없는 말을 있다고 인식하는 문제입니다.

실제 상황에서 환자가 3초간 침묵했는데, STT가 "네네네 알겠습니다"라고 인식하는 경우가 있습니다. 이는 배경 소음을 음성으로 오인하거나, 모델이 자주 나오는 패턴을 과적합하여 기대하기 때문입니다.

**해결: 오디오 기반 검증**

프롬프트 지침으로 "오디오에서 해당 발화가 들리지 않으면 삭제"하도록 안내합니다. 다만 불확실한 경우(잘 안 들리지만 있을 수도 있는 경우)에는 원본을 유지합니다.

### 6.3 DTMF 메시지 처리

DTMF는 키패드 입력 신호로, 음성이 아닙니다.

환자가 주민번호 뒷자리 0-0-0-1-0-2를 입력하면 대화 기록에 "DTMF: 0", "DTMF: 0", "DTMF: 0", "DTMF: 1", "DTMF: 0", "DTMF: 2"와 같이 6개의 메시지가 기록됩니다.

**문제: Ghost Message로 오인**

오디오에서 "DTMF: 0" 발화가 안 들립니다 (당연히, 키패드 입력이니까). 이를 Ghost Message로 판단해서 삭제하면 중요한 정보가 손실됩니다.

**해결: DTMF 예외 처리**

프롬프트에 명시적으로 "DTMF messages are keypad input signals, NOT voice. No audio exists for DTMF — do NOT treat as ghost messages. Preserve EVERY DTMF message exactly as-is. Do NOT deduplicate, merge, or delete any DTMF messages. Set start_time to null for DTMF messages."라고 지침을 추가했습니다.

### 6.4 운영시간 구분

상담원 연결 요청이 있었지만 연결되지 않은 경우, **운영시간 내/외**를 구분해야 합니다.

운영시간 내 미연결은 즉시 콜백이 필요하고, 운영시간 외 미연결은 다음 영업일에 처리합니다.

분석 결과 발행 시 `agent_consultation_request`가 True인 경우, 운영시간 상태(운영시간 내/외)에 따라 해당 상태 플래그 필드를 설정합니다.

## 7. 비즈니스 로직 연동

### 7.1 예약 모드별 분기 처리

병원마다 예약 처리 방식이 다릅니다:

| 모드 | 설명 | 동작 |
| ---- | ---- | ---- |
| `ai` | AI 직접 예약 | 예약 처리 컴포넌트가 예약 API 호출 |
| `human` | 상담원 연결 | 상담원에게 전화 전환 |

**human 모드일 때 특수 처리:**

예약신청(상담원 연결) 모드이고, 상담원 연락처가 있으며, 예약 생성이 미완료된 경우(취소/변경 요청이 아닌 경우), 상담원 처리 예약 요청 플래그를 True로 설정합니다.

**왜 이런 분기가 필요한가?**

human 모드에서 환자가 "예약하고 싶어요"라고 하면 AI가 "상담원에게 연결해드릴게요"라고 응답합니다. 상담원 연결을 시도했지만 실패한 경우, 분석 결과로 `reservation_creation_incomplete = True`(예약 시작했으나 미완료)와 상담원 처리 예약 요청 플래그(True)가 설정됩니다. 백엔드에서는 이를 바탕으로 "상담원 콜백 필요" 리스트에 추가합니다.

### 7.2 분석 결과 활용

분석 결과는 다양한 용도로 활용됩니다:

**1. 대시보드 통계**

오늘 통화 분석 결과로 총 통화 150건 중 예약 완료 45건(30%), 긍정 응답 82건(55%), 상담원 필요 23건(15%, 운영시간 내 15건/운영시간 외 8건), 인사 중 끊김 12건(8%) 등의 통계를 생성합니다.

**2. 상담원 업무 큐**

콜백 필요 목록을 자동 생성합니다. 예를 들어 "010-1234-5678 - 예약 변경 요청 (운영시간 내)", "010-2345-6789 - 상담원 연결 실패 (운영시간 내)", "010-3456-7890 - 불분명한 응답 (확인 필요)" 등입니다.

**3. 품질 개선 피드백**

"인사 중 끊김" 비율이 높은 경우 인사말이 너무 긴지, 목소리 톤 조정이 필요한지, 통화 시간대 최적화가 필요한지 등을 검토합니다.

## 8. 마치며

### 8.1 배운 점

**1. STT 품질은 후처리로 개선 가능**

실시간 STT의 한계를 받아들이고, 사후에 오디오를 다시 들어서 교정하는 접근이 효과적이었습니다. 실시간 처리는 빠르지만 부정확할 수 있고, 사후 교정은 정확하지만 시간이 소요됩니다. 둘 다 필요합니다. 실시간으로 통화하고, 사후에 교정합니다.

**2. LLM + Hard Rules 조합**

LLM만으로는 모든 케이스를 정확히 처리하기 어렵습니다. 명확한 기준이 있는 경우(로그 기반 판단)는 규칙으로 보정하는 것이 안정적입니다.

LLM의 장점은 맥락 이해와 유연한 판단이고, 단점은 가끔 틀리고 일관성이 부족하다는 것입니다. Hard Rules의 장점은 100% 일관성과 예측 가능성이고, 단점은 유연성 부족입니다. 조합이 최선입니다.

**3. 비동기 파이프라인의 장점**

분석 서비스를 독립적으로 운영하면 분석 실패해도 통화 서비스에 영향이 없고, 분석 로직 변경 시 별도 배포가 가능하며, 부하에 따라 독립적 스케일링이 가능합니다.

### 8.2 향후 개선 방향

**1. 실시간 분석**

통화가 끝난 후가 아니라, **통화 중에** 인사이트를 제공하면 어떨까요? 환자 감정 분석(부정적이면 상담원 연결 제안), 의도 예측(예약 변경하려는 것 같음), 실시간 가이드(이 환자는 이전에 취소 이력 있음) 등을 제공할 수 있습니다.

**2. 다국어 전사 품질 향상**

현재 한국어 중심이지만, 외국어 환자 대응 시 전사 품질 개선이 필요합니다.

**3. 피드백 루프**

분석 결과가 맞았는지 검증하고, 틀린 경우 모델/프롬프트를 개선하는 루프가 필요합니다. 분석 결과 → 상담원 확인 → 피드백 수집 → 프롬프트 개선 → 더 나은 분석의 순환 구조입니다.
