## 1. 들어가며

### 1.1 병원 전화 업무의 현실

병원에 전화해본 경험이 있으신가요?

```
"예약 확인하려고 전화했는데 10분째 통화 대기 중..."
"점심시간이라 전화 안 받네요..."
"진료시간 물어보려고 했는데 상담원 연결까지 너무 오래 걸려요"
```

병원 입장에서도 마찬가지입니다. 하루에 수백 통의 전화가 오지만, 상당수는 비슷한 질문의 반복입니다.

| 문의 유형 | 비율 | 특징 |
|----------|------|------|
| 예약 조회/변경 | 40% | 단순 CRUD, 자동화 가능 |
| 진료시간/위치 안내 | 25% | 정형화된 정보 |
| 의료진/진료과 문의 | 20% | 검색 기반 응답 가능 |
| 복잡한 상담 | 15% | 상담원 필요 |

**85%의 전화가 AI로 처리 가능한 단순 업무**라는 점에 주목했습니다.

### 1.2 음성 AI로 해결하려는 문제

우리가 만들고자 한 것은 **24시간 응대 가능한 병원 AI 전화 비서**입니다.

**목표:**
- 예약 조회, 생성, 변경을 AI가 직접 처리
- 병원 정보(진료시간, 위치, 의료진 등)를 즉시 안내
- 복잡한 문의는 상담원에게 연결
- 자연스러운 한국어 음성 대화

**기대 효과:**
- 환자: 대기 시간 없이 즉시 응대
- 병원: 상담 인력의 복잡한 업무 집중 가능
- 24시간: 야간/주말에도 기본 문의 처리

### 1.3 이 글에서 다루는 내용

이 글에서는 LiveKit Agents 프레임워크를 사용해 병원 음성 AI를 구축한 경험을 공유합니다.

**다루는 내용:**
- Multi-Agent 아키텍처 설계 (InfoAgent + BookingAgent)
- Qdrant 벡터 DB를 활용한 병원 정보 검색
- 멀티턴 예약 대화 처리 (AgentTask)
- 실전에서 마주친 문제들과 해결 방법

**다루지 않는 내용:**
- LiveKit 서버 설치/설정 (공식 문서 참조)
- SIP 트렁크 세부 설정
- 프론트엔드 구현

그럼 시작해보겠습니다.

## 2. 기술 스택 및 아키텍처

### 2.1 왜 LiveKit Agents인가?

음성 AI를 구축하려면 여러 선택지가 있습니다. Twilio, Vonage, 직접 WebRTC 구현 등. 우리가 LiveKit Agents를 선택한 이유는 다음과 같습니다.

**LiveKit Agents의 장점:**

| 특징 | 설명 |
|------|------|
| **실시간 양방향 통신** | WebRTC 기반으로 지연 시간 최소화 |
| **Python 네이티브** | AI/ML 생태계와 자연스러운 통합 |
| **Multi-Agent 지원** | 여러 Agent 간 전환이 프레임워크 레벨에서 지원 |
| **SIP 통합** | 기존 전화망과 연동 가능 |
| **OpenAI Realtime API 지원** | 음성-to-음성 직접 처리로 레이턴시 감소 |

특히 **Multi-Agent 전환**이 내장되어 있다는 점이 결정적이었습니다. 예약 Agent와 정보 Agent를 분리하고 동적으로 전환하는 것이 자연스럽게 가능했습니다.

### 2.3 핵심 구성 요소

#### LiveKit Agents 프레임워크

LiveKit Agents는 `Agent` 클래스를 상속받아 구현합니다. `instructions`에 시스템 프롬프트를, `tools`에 사용할 함수들을 등록하는 방식입니다.

#### OpenAI Realtime API

기존 방식은 `음성 → STT → LLM → TTS → 음성`의 파이프라인이었습니다. OpenAI Realtime API는 이를 단일 호출로 처리해 레이턴시를 크게 줄입니다.

```
기존: 음성 → [STT] → 텍스트 → [LLM] → 텍스트 → [TTS] → 음성
          (200ms)         (500ms)         (200ms)

Realtime: 음성 → [OpenAI Realtime] → 음성
                    (300ms~)
```

#### Qdrant 벡터 DB

병원 정보(의료진, 진료과, 이벤트 등)는 Qdrant 벡터 DB에 저장하고 시맨틱 검색합니다. 토픽별 메타데이터 구조로 병원별, 카테고리별 필터링이 가능합니다.

#### LiveKit SIP

실제 전화망과 연동하기 위해 SIP 트렁크를 사용합니다. LiveKit이 SIP 게이트웨이 역할을 해서 일반 전화로 발신/수신이 가능합니다.

### 2.4 통화 라이프사이클

아웃바운드 콜의 전체 생명주기는 다음과 같은 상태 전이를 거칩니다.

```
IDLE → DIALING → RINGING → CONNECTED → ACTIVE → TERMINATED
  │       │         │          │         │          │
  │       │         │          │         │          └─→ ANALYZED
  │       │         │          │         │
  │       │         │          │         └─→ TRANSFERRED → TERMINATED
  │       │         │          │
  │       │         │          └─→ RECORDING_STARTED
  │       │         │
  │       │         └─→ NO_ANSWER → TERMINATED
  │       │
  │       └─→ BUSY → TERMINATED
  │
  └─→ ERROR → TERMINATED
```

**주요 단계:**

| 단계 | 설명 | 트리거 |
|------|------|--------|
| **IDLE** | 대기 상태 | Job 수신 |
| **DIALING** | 발신 중 | SIP 트렁크 호출 |
| **RINGING** | 벨 울림 | 상대방 전화기 연결 |
| **CONNECTED** | 연결됨 | 상대방 응답 |
| **ACTIVE** | 대화 진행 | 인사말 전송 |
| **TERMINATED** | 종료 | 통화 완료/실패 |
| **ANALYZED** | 분석 완료 | MQ 메시지 처리 |

### 2.5 다국어 지원

음성 AI에서 다국어 지원은 단순히 텍스트 번역이 아닙니다. 음성 인식(STT)과 음성 합성(TTS)이 모두 해당 언어를 지원해야 합니다.

**지원 언어:**

| 언어 | 코드 | 비고 |
|------|------|------|
| 한국어 | ko-KR | 기본 언어 |
| 영어 | en-US | - |
| 중국어 | zh-CN | 간체 |
| 일본어 | ja-JP | - |
| 스페인어 | es-ES | - |
| 베트남어 | vi-VN | - |

**구현 방식:**
- `CallConfigData`에서 언어 코드 설정 (예: "ko-KR")
- LLM 모델 파라미터에 해당 언어 전달
- 프롬프트에 "해당 언어만 사용" 제약 조건 추가

## 3. Multi-Agent 설계 철학

### 3.1 단일 Agent의 한계

처음에는 하나의 Agent로 모든 기능을 처리하려 했습니다.

**문제점:**
- 프롬프트가 200줄을 넘어가면서 모델이 지시사항을 놓치는 경우 발생
- 도구가 14개가 되니 잘못된 도구를 호출하는 빈도 증가
- 예약 로직 수정 시 정보 안내에 영향을 줄까 걱정되어 유지보수 어려움

### 3.2 역할 기반 Agent 분리 전략

해결책은 **역할별로 Agent를 분리**하는 것이었습니다.

```
Before (단일 Agent):
┌─────────────────────────────────┐
│         HospitalAgent           │
│  프롬프트: 200줄 | 도구: 14개    │
│  역할: 예약 + 정보 + 전환 + ...  │
└─────────────────────────────────┘

After (Multi-Agent):
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│TriageCoordinator│  │  BookingAgent   │  │    InfoAgent    │
│ 프롬프트: 40줄   │  │ 프롬프트: 50줄  │  │ 프롬프트: 40줄   │
│ 도구: 3개       │  │ 도구: 5개       │  │ 도구: 6개        │
│ 역할: 의도 분류  │  │ 역할: 예약 처리  │  │ 역할: 정보 안내  │
└─────────────────┘  └─────────────────┘  └─────────────────┘
```

**분리 후 개선점:**

| 항목 | Before | After |
|------|--------|-------|
| 프롬프트 길이 | 200줄 | 각 40~50줄 |
| Agent당 도구 수 | 14개 | 3~6개 |
| 도구 오호출률 | 높음 | 현저히 감소 |
| 유지보수성 | 낮음 | 높음 (독립적 수정 가능) |

### 3.3 Agent 역할 정의

#### TriageCoordinator (의도 분류)

사용자의 첫 발화를 듣고 적절한 Agent로 라우팅합니다.
- 예약 관련 → BookingAgent로 전환
- 정보 문의 → InfoAgent로 전환
- 상담원 요청 → 상담원 연결 처리

#### BookingAgent (예약 처리)

예약 조회, 생성, 수정을 전담합니다.
- 진료과 선택
- 날짜/시간 선택
- 예약 생성

#### InfoAgent (정보 안내)

병원 정보 검색 및 안내를 전담합니다.
- 병원 소개, 진료시간
- 오시는 길, 주차
- 의료진, 진료 서비스, 이벤트

### 3.4 BaseAgent 공통 기능 추출

세 Agent 모두 필요한 공통 기능을 `BaseAgent`로 추출했습니다.

**공통 기능 목록:**
- `on_enter()`: Agent 진입 시 컨텍스트 처리
- `_transfer_to_agent()`: Agent 간 전환
- `transfer_call()`: 상담원 연결
- `end_call_by_user_request()`: 통화 종료
- `hangup()`: Room 삭제

이렇게 공통 기능을 BaseAgent에 모아두면 각 Agent는 자신의 역할에만 집중할 수 있습니다.

## 4. InfoAgent 구현하기

### 4.1 병원 정보 검색의 요구사항

InfoAgent가 처리해야 하는 정보 유형을 정리하면 다음과 같습니다.

| 카테고리 | 예시 질문 | 데이터 특성 |
|---------|----------|------------|
| **병원 소개** | "병원이 어떤 곳이에요?" | 정적, 텍스트 |
| **진료시간** | "토요일에도 진료하나요?" | 정적, 구조화 |
| **오시는 길** | "주차 가능한가요?" | 정적, 텍스트 |
| **의료진** | "김철수 원장님 전문 분야가?" | 검색 필요, 다수 |
| **진료 서비스** | "임플란트 비용이 얼마예요?" | 검색 필요, 다수 |
| **이벤트** | "지금 하는 할인 있어요?" | 동적, 기간 필터 필요 |

**핵심 요구사항:**
1. **시맨틱 검색**: "김 원장님" → "김철수 원장" 매칭
2. **필터링**: 토픽별, 병원별 데이터 분리
3. **동적 데이터**: 이벤트 기간 체크

### 4.2 Qdrant 벡터 DB 활용

#### 토픽별 데이터 구조화

모든 병원 정보를 단일 컬렉션에 저장하되, 메타데이터로 분류합니다.

**토픽 분류 체계:**

| topic | sub_topic | 설명 |
|-------|-----------|------|
| `INTRODUCTION` | `INFO`, `OPENING_HOURS`, `PROCEDURE`, `NOTICE` | 병원 소개 |
| `VISIT_GUIDE` | `PARKING`, `PUBLIC_TRANSPORT`, `FACILITY_LOCATIONS` | 방문 안내 |
| `MEDICAL_STAFF` | - | 의료진 정보 |
| `MEDICAL_SERVICE` | - | 진료 서비스 |
| `EVENT` | - | 이벤트/프로모션 |

#### 메타데이터 필터링 전략

검색 시 반드시 `client.id`와 `topic`으로 필터링하여 정확한 데이터만 반환합니다.

### 4.3 정보 검색 도구 설계

InfoAgent에서 사용하는 주요 도구들입니다.

| 도구 | 기능 | 특이사항 |
|------|------|---------|
| `get_introduction` | 병원 소개, 진료시간 조회 | sub_topic으로 세부 분류 |
| `get_visit_guide` | 오시는 길, 주차 안내 | 교통편별 필터링 |
| `get_medical_staffs` | 의료진 정보 검색 | 시맨틱 검색으로 유사 매칭 |
| `get_medical_services` | 진료 서비스 안내 | 가격, 절차 포함 |
| `get_events` | 이벤트/프로모션 검색 | 기간 필터링 적용 |

### 4.4 핵심 설계 포인트

**InfoAgent 설계 시 중요한 점들:**

1. **역할 명확화**: "정보 안내 담당자"로 범위 한정
2. **추측 금지**: 도구 검색 결과만 사용하도록 강조
3. **전환 규칙**: 예약 문의 시 BookingAgent로 전환
4. **응답 예시**: 기대하는 동작 패턴 제시

## 5. BookingAgent 구현하기

### 5.1 예약 플로우 설계

병원 예약은 단순해 보이지만 여러 단계가 필요합니다.

```
사용자: "예약하고 싶어요"
          │
          ▼
    ┌─────────────┐
    │ 진료과 선택  │ ← get_medical_departments()
    └──────┬──────┘
           │
           ▼
    ┌─────────────┐
    │ 날짜 확인   │ ← "다음주 화요일" → "2024-12-17"
    └──────┬──────┘
           │
           ▼
    ┌─────────────┐
    │ 시간 선택   │ ← select_available_schedules()
    └──────┬──────┘
           │
           ▼
    ┌─────────────┐
    │ 예약 생성   │ ← add_new_appointment()
    └──────┬──────┘
           │
           ▼
    "예약이 접수되었습니다"
```

**핵심 과제:**
- 자연어 날짜 ("다음주 화요일") → ISO 날짜 변환
- 멀티턴 대화로 정보 수집 (날짜 → 시간 → 확인)
- 중간에 이탈하거나 변경 요청 대응

### 5.2 예약 도구 개요

BookingAgent에서 사용하는 주요 도구들입니다.

| 도구 | 기능 | 특이사항 |
|------|------|---------|
| `get_my_appointment_list` | 기존 예약 내역 조회 | 환자 정보로 필터링 |
| `get_medical_departments` | 예약 가능 진료과 목록 | 초진/재진 구분 |
| `select_available_schedules` | 날짜/시간 선택 | AgentTask로 멀티턴 처리 |
| `add_new_appointment` | 예약 생성 | 생년월일 미등록 시 수집 |

### 5.3 멀티턴 대화 처리: AgentTask 활용

예약 시간 선택은 여러 턴의 대화가 필요합니다. LiveKit의 `AgentTask`를 활용해 이를 구현했습니다.

#### AgentTask란?

일반 `function_tool`은 한 번 호출되고 끝나지만, `AgentTask`는 **자체적인 대화 루프**를 가질 수 있습니다.

#### ScheduleSelectionTask 상태 흐름

```
collect_date → confirm_date → select_time → complete
```

1. **collect_date**: 원하는 날짜 질문
2. **confirm_date**: 해석한 날짜 확인 ("12월 17일 맞으신가요?")
3. **select_time**: 가능한 시간 안내 및 선택
4. **complete**: 선택 완료, Task 종료

### 5.4 예약 플로우 요약

| 단계 | 도구 | 설명 |
|------|------|------|
| 1 | `get_medical_departments` | 진료과 선택 |
| 2 | `select_available_schedules` | 날짜/시간 선택 (멀티턴 Task) |
| 3 | `add_new_appointment` | 예약 생성 |

## 6. Agent 간 전환 (라우팅)

### 6.1 TriageCoordinator의 역할

TriageCoordinator는 **교환원** 역할을 합니다. 전화를 받아 용건을 파악하고, 적절한 담당자(Agent)에게 연결합니다.

```
┌─────────────────────────────────────────────────────────┐
│                   TriageCoordinator                      │
│                                                          │
│  사용자: "예약하고 싶어요"                                │
│                │                                         │
│                ▼                                         │
│  ┌─────────────────────────┐                            │
│  │ 의도 분류               │                            │
│  │ - 예약 키워드 감지      │                            │
│  │ - route_to_booking 호출 │                            │
│  └───────────┬─────────────┘                            │
│              │                                           │
│              ▼                                           │
│  ┌─────────────────────────┐                            │
│  │ BookingAgent로 전환     │                            │
│  │ + 사용자 발화 전달      │                            │
│  └─────────────────────────┘                            │
└─────────────────────────────────────────────────────────┘
```

**TriageCoordinator가 처리하는 분기:**

| 사용자 의도 | 키워드 예시 | 호출 도구 |
|------------|------------|----------|
| 예약 | "예약", "일정", "시간 변경" | `route_to_booking` |
| 정보 문의 | "진료시간", "의사", "주차" | `route_to_info` |
| 상담원 연결 | "상담원", "사람", "직원" | `transfer_call` |
| 자동응답기 | (beep 소리 감지) | `detected_answering_machine` |

### 6.2 컨텍스트 전달 방식

Agent 전환 시 **사용자의 원본 발화**를 다음 Agent에 전달해야 합니다. 그렇지 않으면 다음 Agent가 처음부터 다시 질문해야 합니다.

```
# 잘못된 예: 컨텍스트 전달 없음
사용자: "내과 예약하고 싶어요"
Triage → Booking 전환
Booking: "어떤 진료과로 예약하시겠어요?" ← 다시 물어봄 (UX 나쁨)

# 올바른 예: 컨텍스트 전달
사용자: "내과 예약하고 싶어요"
Triage → Booking 전환 (user_request="내과 예약하고 싶어요")
Booking: "내과 예약 도와드리겠습니다. 날짜는 언제가 좋으세요?" ← 자연스러움
```

### 6.3 오디오 입력 제어 (set_audio_enabled)

Agent 전환 중에 사용자가 계속 말하면 혼선이 생깁니다. 이를 방지하기 위해 **전환 중 오디오 입력을 일시 차단**합니다.

**왜 필요한가?**

```
Without audio control:
User: "예약하고 싶어요 내과로요 다음주에"
       ├── Triage가 "예약" 듣고 전환 시작
       ├── "내과로요 다음주에"가 Triage에 남음
       └── Booking이 받지 못함 → 다시 질문해야 함

With audio control:
User: "예약하고 싶어요"
       ├── Triage: route_to_booking 호출
       ├── set_audio_enabled(False) → 입력 차단
       ├── Agent 전환 완료
       ├── set_audio_enabled(True) → 입력 재개
       └── User: "내과로요" → Booking이 정상 수신
```

## 7. 실전에서 마주친 문제들

### 7.1 자연어 날짜/시간 파싱

사용자는 "2024-12-20" 같은 형식으로 말하지 않습니다.

**실제 사용자 발화:**
- "다음주 화요일"
- "이번 달 말쯤"
- "크리스마스 전날"
- "내일 오전"
- "12일" (월 생략)

#### 해결 전략

규칙 기반 파싱은 한계가 있어서, **LLM을 활용해 자연어를 ISO 날짜로 변환**합니다.

오늘 날짜와 사용자 표현을 함께 전달하면 LLM이 "다음주 화요일" 같은 표현을 "2024-12-17" 형식으로 변환해줍니다.

한국어 시간 표현("오전 9시", "오후 3시 30분")도 별도 파싱 로직으로 처리합니다.

### 7.2 사용자 무응답 처리

전화를 받고 아무 말도 안 하는 케이스가 의외로 많습니다.

**무응답 시나리오:**
- 전화 받았는데 주변이 시끄러워서 못 들음
- 전화 받고 다른 일 하느라 응답 못함
- 자동응답기가 받음

#### 해결 전략: user_state_changed 이벤트 활용

LiveKit은 사용자 상태 변화를 이벤트로 알려줍니다.

- `away` 상태가 되면 확인 태스크 시작
- 사용자가 말하면 태스크 취소
- 2회 무응답 시 통화 종료

### 7.3 상담원 연결 Fallback

AI가 모든 것을 처리할 수 없습니다. 상담원 연결이 필요한 경우:

- 사용자가 명시적으로 요청 ("상담원 연결해주세요")
- AI가 처리할 수 없는 복잡한 문의
- 긴급 상황

#### 해결 전략

설정에 따라 동작이 달라집니다.

- **AI 예약 모드**: BookingAgent가 직접 예약 처리
- **상담원 연결 모드**: SIP 전환 시도
- **전환 번호 미설정**: 메시지만 수집하고 종료

### 7.4 자동 응답기(ARS) 감지

발신 전화가 자동응답기로 연결되는 경우가 있습니다. 이때 AI가 계속 대화를 시도하면 안 됩니다.

**감지 조건 (3가지 모두 충족 필요):**

| 조건 | 설명 | 예시 |
|------|------|------|
| **자동화된 인사말** | 녹음된 안내 메시지 | "소리샘 서비스입니다", "음성 사서함입니다" |
| **버튼 입력 안내** | IVR 메뉴 프롬프트 | "1번을 눌러주세요", "삐 소리 후 메시지를 남겨주세요" |
| **프롬프트 반복/루프** | 인간 개입 없이 반복 | 동일 메시지 2회 이상 반복 |

**왜 3가지 조건 모두 필요한가?**

```
조건 1개만 체크 → 오탐 높음
  예: "안녕하세요" 자동 인사 ≠ 자동응답기

조건 3개 모두 체크 → 정확도 높음
  예: 자동 인사 + 버튼 안내 + 반복 = 확실한 자동응답기
```

감지 시 통화를 종료하고 히스토리에 감지 이벤트를 기록합니다.

### 7.5 프롬프트 시스템 구조

음성 AI의 품질은 프롬프트 설계에 크게 좌우됩니다. YAML 형식으로 구조화된 프롬프트를 사용합니다.

**프롬프트 구성 섹션:**

| 섹션 | 역할 | 예시 |
|------|------|------|
| **Role** | 역할 정의 | "병원 예약 상담 AI 비서" |
| **Personality & Tone** | 성격/톤 설정 | "친근하고 전문적, 2-3문장 이내" |
| **Instructions** | 핵심 지침 | "추측 금지, 도구 결과만 사용" |
| **Tools** | 도구 사용 가이드 | "예약: departments → operators → dates" |
| **Conversation Flow** | 대화 흐름 | "인사 → 메인 대화 → 종료" |
| **Safety & Escalation** | 안전 규칙 | "상담원 요청 시 즉시 전환" |

**대화 흐름 규칙:**

```
1. 인사 (최대 2회 시도)
   └─ Turn 1: 초기 인사
   └─ Turn 2: 병원명 + 목적 (간략)
   └─ Turn 2+: 인사 시도 안 함

2. 메인 대화
   └─ 사용자 요청 처리
   └─ 도구 호출

3. 종료
   └─ 요약 + 인사
```

**Safety & Escalation 규칙:**

| 상황 | 동작 | 확인 필요 |
|------|------|----------|
| 명시적 상담원 요청 | 즉시 전환 | ❌ |
| 예약 변경/취소 | 확인 후 전환 | ✅ |
| 불만/욕설 | 확인 후 전환 | ✅ |
| 정보 수집 실패 | 확인 후 전환 | ✅ |

## 8. 통화 종료 및 후처리

### 8.1 종료 시나리오별 처리

통화 종료는 여러 경로로 발생합니다. 각 시나리오에 맞는 처리가 필요합니다.

| 시나리오 | 트리거 | 처리 |
|---------|-------|------|
| **사용자 요청** | "끊을게요", "통화 끝" | 감사 인사 후 종료 |
| **시스템 종료** | 무응답, 오류, 작업 완료 | 안내 후 종료 |
| **상담원 전환** | SIP 전환 성공 | Room 유지 (AI 퇴장) |
| **연결 끊김** | 사용자가 먼저 끊음 | 즉시 정리 |

### 8.2 세션 종료 후 처리

통화가 종료되면 여러 후처리 작업이 필요합니다.

**후처리 작업 목록:**

1. **녹음 중지**: Egress 중지 및 파일 저장
2. **통화 완료 알림**: MQ 메시지 발행 (aiu-agent-call-complete)
3. **대화 분석 요청**: MQ 메시지 발행 (aiu-agent-call-start-analysis)
4. **트랜스크립트 저장**: 로컬 환경에서 디버깅용 저장

**분석 서비스로 전송되는 데이터:**
- 통화 세션 정보 (room_name, recipient, business, 시간 정보)
- 전체 대화 내역 (role, content)

## 9. 마무리

### 9.1 배운 점

#### Multi-Agent의 힘

단일 Agent로 모든 걸 처리하려다 프롬프트 200줄, 도구 14개가 되었을 때의 혼란을 겪고 나서, **역할 분리의 중요성**을 체감했습니다.

```
Before: 하나의 만능 Agent → 복잡, 불안정, 유지보수 어려움
After: 역할별 전문 Agent → 단순, 안정, 독립적 수정 가능
```

#### 프레임워크 선택의 중요성

LiveKit Agents는 Multi-Agent 전환, 음성 처리, SIP 통합을 프레임워크 레벨에서 지원해서 개발 속도가 빨랐습니다. 직접 WebRTC를 다루거나 Agent 전환 로직을 구현했다면 훨씬 오래 걸렸을 것입니다.

#### 실제 사용자는 예상과 다르게 행동

- "다음주 화요일" 같은 자연어 날짜 표현
- 전화 받고 아무 말 안 하는 케이스
- 중간에 갑자기 다른 질문으로 전환

규칙 기반으로는 한계가 있어서 LLM 활용이 필수였습니다.

### 9.2 개선하고 싶은 점

#### 대화 흐름 개선

현재는 단계별로 질문하는 방식인데, 사용자가 한 번에 많은 정보를 말할 때 더 잘 처리하고 싶습니다.

```
현재: "날짜요?" → "12월 17일" → "시간요?" → "오전 10시"
목표: "12월 17일 오전 10시로 예약해주세요" → 한 번에 처리
```

#### 모니터링 대시보드

통화 성공률, 평균 처리 시간, 자주 묻는 질문 등을 실시간으로 볼 수 있는 대시보드가 필요합니다.

### 9.3 다음 글 예고

다음 글에서는 더 심화된 주제를 다룰 예정입니다:

- **AgentTask 심층 분석**: 복잡한 멀티턴 대화 패턴 구현
- **성능 최적화**: 레이턴시 줄이기, 프롬프트 튜닝
- **통화 분석 파이프라인**: 대화 내용 분석 및 인사이트 추출
